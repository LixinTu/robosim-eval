# 真实缺陷记录:复现、修复与同条件复跑(计划 A1)

下面四个都是本项目评测工具自身的真实缺陷,在真实 Isaac 运行中暴露。它们不是故障注入;故障注入只用在 D3 的 cancel、dropout、timeout、collision 情形,那些在配置里有标注。每个缺陷都保留了修复前的失败证据和修复后同条件复跑的证据。

## 缺陷 1:停稳确认用了结果之前的样本(D2)

| 项目 | 内容 |
| --- | --- |
| 现象 | 真实运行 `artifacts/d2/runs/normal-20260930-003622`:Nav2 在仿真 22.5 s 返回 SUCCEEDED,运行器却在 22.85 s 就确认"停稳",只隔 0.35 s,不可能满足"静止 1 s"。录制随即停止,离线分析只看到结果之后 0.35 s 的数据,判"停稳无法观察",评测 inconclusive |
| 根因 | 停稳跟踪器被喂进了缓存里的全部 odom 样本,包括结果之前的;机器人接近目标时已在减速,静止窗口从结果之前就开始计 |
| 修复 | 提交 `d4756d0`:跟踪器只吃结果之后的样本;确认后记录器多录 3 s |
| 回归测试 | 假节点测试新增断言"停稳确认至少晚于终态 1 s":修复前失败(`artifacts/d2/fake-04-red`),修复后通过(`artifacts/d2/fake-04`) |
| 同条件复跑 | 同一情形、同一配置:`artifacts/d2/runs/normal-20260930-004343`。终态 25.43 s,停稳确认 26.5 s(晚 1.07 s),到达判定时刻为停稳确认时刻,任务结果 reached |

## 缺陷 2:复位前的 odom 样本留在缓存里(D3)

| 项目 | 内容 |
| --- | --- |
| 现象 | 真实运行 `artifacts/d3/runs/cancel-20260930-010644` 与 `timeout-20260930-011202`:取消后机器人完全静止(线速度约 0.0007 m/s),运行器却在 10 s 后报停车确认超时,判 error 并要求中止批次 |
| 复现与诊断 | 加诊断后重跑 `artifacts/d3/runs/cancel-20260930-012218`:跟踪器吃进了一个时间戳 46.48 s 的样本,而当时仿真时钟只有 15.8 s |
| 根因 | 运行器在复位前就订阅 odom,缓存里留着复位之前那条时间线的样本;复位后时钟从 0 开始,旧样本的时间戳反而更大,之后所有新样本都被当成"更早"而跳过。正常到达的运行没出现,是因为导航时间足够长,旧样本早被挤出缓存 |
| 修复 | 提交 `4332d79`:`runner_fsm.append_sample` 遇到时间戳倒退就丢弃旧时间线;2 个固定输入测试先失败后通过 |
| 同条件复跑 | `artifacts/d3/runs/cancel-20260930-012426`:CANCELED 后 1.02 s 确认停稳,评测 pass;`artifacts/d3/runs/timeout-20260930-012837`:仿真时限触发取消,评测 pass |

## 缺陷 3:场景未加载时接触监视装不上(D5)

| 项目 | 内容 |
| --- | --- |
| 现象 | Isaac 刚启动、场景还没加载时跑第一次运行:运行器会自己加载场景,机器人也正常到达,但安全结论是 unknown,整体 inconclusive(退出 11)。原因是接触数据缺失 |
| 发现 | 写 README 时读运行器代码发现:准备阶段先装接触监视,后加载场景 |
| 复现 | 经 sim_control 停止仿真并载入空场景 `tests/assets/empty_stage.usda`(只有一个空的 /World,等同于还没加载场景),再用修复前的代码(`3b58422`)跑 `run_scenario.sh normal`:`artifacts/d5/defect3-before/normal-20260930-020110`。events.jsonl 里先是 `contacts_unavailable`("/World/Nova_Carter_ROS not found"),然后才是 `load_world`;result.json 的理由是 "contact data missing: safety cannot be judged" |
| 根因 | `runner._reset_sim` 的顺序:安装接触监视在"机器人不存在就加载场景"之前。安装时机器人还不存在,Isaac 端返回 not found |
| 修复 | 提交 `12a1544`:先检查并加载场景,再安装接触监视,仍在复位之前(接触报告要在物理重启时生效) |
| 回归证据 | 这一步要真实的 Isaac 场景加载,没有做成固定输入测试;以同条件复跑作为回归证据 |
| 同条件复跑 | 同样先载入空场景,按 README 从新的 PowerShell 跑 `run_scenario.sh normal`:`artifacts/d5/demo/runs/normal-20260930-021122`。事件顺序变为 `load_world` → `contacts_installed`(8 个刚体)→ 复位;安全 pass(实测,无接触),评测 pass |

## 缺陷 4:接受目标时的仿真时间是旧的(D5)

| 项目 | 内容 |
| --- | --- |
| 现象 | 运行器记录的"目标被接受"的仿真时间,比离线分析从 bag 取的接受时刻早 1.1–2.1 s。以它为起点的计时因此都提前:cancel 情形"接受后 5 s 取消"实际发生在真实接受后 3.0–3.7 s,dropout 的暂停在约 3.5 s,timeout 情形的 6 s 仿真时限在约 4.5 s |
| 发现 | D5 参数对比时,两种来源算出的"接受到结果"不一致(normal-021530:运行器 17.43 s,bag 16.2 s),而结果时刻两边完全相同 |
| 复现 | 不需要新运行:D3、D4、D5 的每个真实运行目录都有两种接受时刻(result.json 的 `runner.accept_sim` 与 `timing.sim_time_at_accept_s`)。修复前的 27 次里,26 次偏差 1.1–2.1 s,1 次 0.07 s |
| 根因 | 运行器在发目标前同步调用 `record_d0.sh`,约 4 s 墙钟没有处理订阅回调,手里的 `/clock` 值停在调用之前;发出目标后几毫秒就收到接受,这时记下的就是旧值。EXECUTING 的进入时刻、导航时限和注入计时都以它为起点 |
| 修复 | 提交 `9ae722b`:发目标前先处理已排队的消息,再等一条新到的 `/clock`(`runner_fsm.refresh_clock`);2 个固定输入测试先失败(函数不存在)后通过;假节点测试 10/10 |
| 同条件复跑 | `artifacts/d5/defect4-after/cancel-20260930-023111`:运行器与 bag 的接受时刻只差 0.033 s,取消在真实接受后 4.97 s 发出,评测 pass |
| 影响范围 | 判定结论不变:取消、超时、断流这些情形的结果与预期仍然一致。受影响的是时刻数字:D3 台账里"5 s 后取消""6 s 时限"的实际时刻,以及 D3、D4 文档中"接受后约 38 s 才开始动"(按 bag 的接受时刻约 36.4–37.0 s)。D3、D4 的台账已冻结交审,不回改,以本条为准 |

## 不是缺陷但记下的问题

- 复位后点云发布者约 1.5–2 s 才重建,头几秒可能只有 0–1 帧(`artifacts/d2/repro-doctor-after-reset`)。处理为准备阶段 doctor 的有限重查,不是修改门槛。
- "开头卡住":部分运行在发目标后约 37 s 仿真时间不动(原记约 38 s,见缺陷 4),Nav2 自行恢复后到达。D4 查到大部分机制:机器人开头正好背对全局路径(AMCL 朝向 180°、路径方向 0°),DWB 常选绝对值最小的转向档 +0.0368 rad/s,而直接实验证实机器人对这个指令基本不转(8 s 仿真时间 0.0004 rad),状态不变,控制器就一直选它,直到进度检查触发恢复。DWB 为什么把这一档打分最高没有查明。这不是评测工具的缺陷,判定都正确;详见 `artifacts/d4/commands.md`。
